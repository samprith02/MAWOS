# 04 — Data Model and Dataset Design

Covers R0 requirement **6**. This is a **design decision record, not a schema**. No DDL, no
migrations, no generator code — those are R1.

---

## 1. The decision: new generator, inherited calibration

| Option | Verdict |
|---|---|
| **(a) Patch the existing seed** — keep `backend/app/seed.py`, strip the real institution identity, bolt on rooms and availability | **Rejected** |
| **(b) New generator, reuse the UCI calibration** | **Chosen** |
| **(c) New generator, new calibration from scratch** | **Rejected** |

### Why (a) is rejected

`seed.py` is a single 340-line function that emits an entire institution inline. The v4
schema additions — rooms, room types, teacher availability, lab/theory split, period grids
with breaks, requests, conversations, traces — touch nearly every part of it. Patching means
editing the same lines a rewrite would, while inheriting three liabilities:

- **Real identity is structural, not cosmetic.** `4MT{batch}{letters}{idx}` USNs, `@mite.ac.in`
  emails, a named real principal, and real team USNs in a `TEAM` dict are woven through the
  generation logic, not sitting in a constants block.
- **It is not parameterised for scale.** One `per_section` knob; period grid, section count,
  subject counts and department list are all hardcoded.
- **The shipped-DB convention is fragile.** "400 submitted, 0 verified" is deliberate state
  that must not be consumed by running the pipeline — a footgun documented in `CLAUDE.md`
  precisely because it has cost time. v4 deletes admissions, so this liability goes away
  with it.

### Why (c) is rejected

`ml/calibrate.py`, `ml/data/calibration.json` and `docs/DATASET_METHODOLOGY.md` are the
project's answer to *"did you just invent your data?"* — a Gaussian copula preserving the
real (grade, attendance, prior-failure) correlation structure estimated from **n = 1,044**
UCI Student Performance records, with an explicit threats-to-validity section that confronts
the Portuguese-school-data objection head-on. Discarding that to re-derive it would destroy a
genuine asset for no gain.

### What (b) means concretely

**Carried forward unchanged:** `ml/calibrate.py`, `ml/data/calibration.json`,
`docs/DATASET_METHODOLOGY.md`, and the copula sampling method.

**Deleted:** `ml/train.py`, `ml/models/*.joblib`, the placement RF and scholarship CART, and
`ml/data/placement_synthetic.csv` / `scholarship_synthetic.csv`.

**Rewritten:** the generator itself, as a package rather than a function.

## 2. Deleting the two ML models

Recorded here because it is a deliberate reduction, and because it is the one place where an
external objection and this analysis converged independently.

`EligibilityAgent` loads `scholarship_cart.joblib` and scores students on it. Per
`docs/DATASET_METHODOLOGY.md` §3, the training label is generated by *"banded committee
scoring (income slabs, CGPA/attendance bands) + N(0, 0.15) committee noise + 3% label
flips"*. That is: **we wrote a rule, generated labels from it, trained a model to recover the
rule, and then called the model's output AI.** The placement RF has the same shape.

This is circular, it is the objection your guide already raised, and it is indefensible under
questioning. The rules themselves are fine and stay — scholarship eligibility genuinely *is*
a banded policy decision, and stating it as a deterministic rule with reason codes is both
more honest and more useful than predicting it.

**`07_CONTRIBUTION.md` §3 records "no ML model" as a deliberate design position**, not an
omission: this system uses deterministic rules where the domain is deterministic, constrained
search where the problem is combinatorial, and an LLM only for language and planning. That is
a defensible engineering stance and a better answer than an accuracy figure for a model that
learned our own rule.

## 3. Institution identity as configuration

**Requirement:** the final project must not depend on any real institution's identity or data.

**Mechanism:** a single `data/institution.yaml`. Nothing in code hardcodes an institution
name, USN prefix, email domain, or crest ever again.

```yaml
institution:
  name:          "<fictional institution name>"
  short_name:    "<abbrev>"
  usn_prefix:    "<prefix>"          # must not be 4MT
  email_domain:  "<domain>"          # must not be mite.ac.in
  established:   <year>
  affiliation:   "<fictional or generic>"

calendar:
  days:          [Mon, Tue, Wed, Thu, Fri]
  periods:       [ ... ]             # label + start/end
  break_slots:   [ ... ]             # slot indices never scheduled

departments:
  - code: "<code>"
    name: "<name>"
    intake: <n>
    sections_per_year: <n>

rooms:
  - code: "<code>"
    type: "classroom" | "lab" | "seminar"
    capacity: <n>
    building: "<name>"

generation:
  seed: <int>
  students_per_section: <n>
  faculty_per_department: <n>
  attendance_days: <n>
  unavailability_rate: <float>       # fraction of faculty-slots blocked
```

**Constraints on the chosen name:** fictional; not a near-collision with a real institution;
used consistently across UI, seed data, emails, and documents. The name itself is the user's
decision and is recorded as open in `OPEN_DECISIONS.md` §D12 until chosen. R1 proceeds with a
placeholder if it is still open — the placeholder is a config value, so changing it later
costs one line.

**Verification gate (R1):** `grep -ri "mite\|mangalore\|4MT" backend/ frontend/ data/` returns
zero hits outside historical v3 documents.

## 4. Entity model

### 4.1 Carried forward from v3, unchanged in shape

`Department` · `User` · `Student` · `Faculty` · `Subject` · `TeachingAssignment` ·
`TimetableSlot` · `AttendanceRecord` · `AttendanceSummary` · `MarksRecord` · `FeeRecord` ·
`ExamSchedule` · `HallTicket` · `ScholarshipAssessment` · `Notification` · `WorkflowEvent`

### 4.2 New entities

| Entity | Purpose | Key fields |
|---|---|---|
| **Room** | Timetable decision variable | code, type, capacity, building |
| **FacultyAvailability** | Unavailability windows from any source (personal, leave, admin duty) | faculty, day, period, reason, source, valid_from/until |
| **PeriodGrid** | Days, period labels, break slots — from `institution.yaml` | (config-materialised) |
| **Request** | The one write-bearing workflow type in MVRS | type, requester, target, payload, state, decided_by, reasons |
| **Conversation** | Per-user dialogue container | owner, started_at, tier_history |
| **ConversationTurn** | One exchange | role, content, resolved_entities, pending_clarification, pending_confirmation, plan_state |
| **TraceRecord** | One step of one turn | turn_id, step, kind (plan/delegate/tool/guard/gate), actor, verdict, payload, latency_ms |
| **GuardDecision** | Every authorisation outcome, allowed **and** blocked | turn_id, actor, capability, target, verdict, reason_code |

### 4.3 Modified entities

| Entity | Change | Why |
|---|---|---|
| `TimetableSlot` | `room` becomes a FK to `Room`, not a cosmetic string | Rooms become a real decision variable (`05_TIMETABLE_SCOPE.md`) |
| `Subject` | add `kind` (theory/lab) and `block_size` | Lab blocks are SHOULD-tier, but the field must exist now or the schema changes twice |
| `Faculty` | add `qualified_subjects` | Substitution search needs it; currently implicit in `TeachingAssignment` |
| `ScholarshipAssessment` | drop `ml_score` | The model is deleted |

### 4.4 Removed entities

`Application` (admissions) · `PlacementShortlist.ml_probability` (the RF is deleted; the
eligibility rule and the shortlist stay).

**`GuardDecision` deserves emphasis.** It is a small table that exists solely so that
*attempted but blocked* actions are counted. `07_CONTRIBUTION.md` claim 1 — that guard
placement rather than model choice determines safety — is unmeasurable without it. If the
guard only logged denials as exceptions, or logged nothing on success, the attempt rate could
not be computed. This is the clearest example in the project of the evaluation instrument
dictating a schema decision, and it belongs in R1 rather than being retrofitted at R5.

## 5. Generator design

`data/generator/`, a package, not a function.

### 5.1 Requirements

1. **Deterministic.** Same `institution.yaml` + same seed → byte-identical output. Verified by
   a test that generates twice and compares hashes.
2. **Scale-parameterised.** Institution size is config, not code. The scalability harness
   needs to sweep it.
3. **Layered.** Structure (departments, subjects, rooms, faculty, assignments) → population
   (students) → history (attendance, marks, fees) → derived (summaries, verdicts). Each layer
   independently regenerable.
4. **Correlation-preserving.** Student academic profiles come from the UCI copula, unchanged.
5. **Feasible by construction.** Generated teaching assignments and availability must admit at
   least one valid timetable — otherwise a solver failure is ambiguous between a solver bug
   and an impossible instance. The generator asserts this before emitting.
6. **No real identity.** All names from fictional name pools; all identifiers derived from
   `institution.yaml`.

### 5.2 Realism decisions

| Aspect | Approach | Justification |
|---|---|---|
| Academic profile (CGPA, attendance, backlogs) | UCI-calibrated Gaussian copula | Preserves real correlation structure; already documented |
| Attendance propensity | Per-student Beta draw, tuned so ~15–20% fall below the 75% rule | Exercises shortage workflows without making the institution look pathological. Carried from v3 |
| Family income | Log-normal, stated as an assumption | No public source pairs Indian income microdata with academic features; disclosed in `DATASET_METHODOLOGY.md` §3 |
| **Faculty unavailability** | Small per-faculty random blocked set, rate from config | **New.** Must be sparse enough that the instance stays feasible (§5.1 rule 5) |
| **Room inventory** | Sized so classrooms comfortably exceed concurrent sections; labs are scarce | **New.** Scarce labs make room allocation a real constraint; abundant classrooms keep the instance feasible |
| Fees | ~15% of students carry an unpaid item | Drives the Compliance cascade |

### 5.3 Fixtures

`tests/fixtures/` — a hand-built miniature institution (2 departments, 4 sections, ~20
students, 6 faculty, 8 rooms) with **fully known ground truth**.

Why this is MUST-tier and not a convenience:

- The R5 outcome checker asserts against exact expected state. That requires an instance small
  enough to reason about by hand.
- Tests currently depend on the 30 MB seeded `mawos.db`, which is why `CLAUDE.md` carries
  warnings about not deleting it while the server runs and not running the evaluation
  concurrently. Fixtures remove that coupling entirely.
- Solver tests need instances where the optimal answer is known, not merely instances that
  produce *an* answer.

## 6. Storage

| Environment | Store | Rationale |
|---|---|---|
| Local development | SQLite | Zero-install; keeps the fast feedback loop |
| Tests | In-memory SQLite + fixtures | No file locking, no shared-state bugs |
| Deployment | **PostgreSQL** | Concurrency, managed free tiers, and it eliminates the file-lock footgun class |

Models are already SQLAlchemy, so this is configuration plus **Alembic** migrations. Adopting
Alembic is MUST-tier: v3 relies on `Base.metadata.create_all` plus a hand-written reseed
helper, which cannot evolve a deployed database.

**Open:** whether the deployed instance actually lands on Postgres depends on the host's free
tier — see `OPEN_DECISIONS.md` §D11.

## 7. What this buys

| Problem in v3 | Resolved by |
|---|---|
| Real institution identity throughout | `institution.yaml` + the R1 grep gate |
| Circular ML models | Deleted; rules kept |
| No rooms → ITC-2007 track 3 descoped | `Room` entity + FK |
| No availability → no leave-driven re-solve | `FacultyAvailability` |
| No conversation memory | `Conversation` / `ConversationTurn` |
| Guard attempts unmeasurable | `GuardDecision` |
| Tests coupled to a 30 MB DB | Fixtures |
| Schema cannot evolve in deployment | Alembic |
| Institution size hardcoded | `generation:` config block |
